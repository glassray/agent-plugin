# Create a Glassray evaluator

Produce an unpublished evaluator version that checks a written deviation recipe on the agreed traces.

Keep evaluator working files uncommitted. If the runner needs a model API key, read it from the environment.

Use plain language in every message to the user, from the first update to the final report. Start with what happened, what you found, or the decision they need to make. Use their words for the work and explain any necessary Glassray term the first time it matters. Keep tool details in the background unless they help the user act. Keep quotes, counts, prices and IDs exact. If the user asks for a simpler explanation, say the same thing in simpler words.

For example, say “The draft checks reports and skips meeting notes. The free check showed that the AI gets both sets of figures it needs to compare, the client’s originals and the ones in the report.”

1. **Start with the known examples.** Identify the requested Glassray workspace and project before searching. Read `get_evaluator_guide`. Look up the existing deviation, its recipe, examples and evaluator drafts first. Create a deviation only when needed. Use the known examples before doing a wider search. Read enough real traces to show a clear case and a close example that should pass or be skipped, when available. Check local model access while gathering evidence, without making a model call. Keep the IDs of traces you read for later calibration. If a filter returns nothing, check whether the project is empty. Offer `glassray-otel` if it needs traces and wait for the user to choose tracing setup.
2. **Agree on the broad scope.** Show what the evaluator would check and skip, and give the exact Glassray filter, view or flow. Explain any extra check the evaluator applies when the filter cannot express the whole scope. Get agreement on new or unsettled scope. Use a real example to ask about the biggest unresolved boundary, such as which documents are in scope or what makes a case count. Ask one yes-or-no question at a time and wait for the answer. Use decisions the user already made. Move on once the broad decisions are clear and keep smaller questions for calibration.
3. **Make the saved recipe match the decision.** Compare the effective recipe with what the user wants, even when a recipe already exists. When they differ, show the changed lines and why, preview with `update_deviation`, and save after the user approves that preview. Test against the recipe version the draft will use. If the recipe decision is pending, show the blocker and keep any work local. Keep the rule in the recipe so the prompt and code give the same instruction.
4. **Choose the model with the user.** If code alone can decide the rule, use code. Otherwise recommend a supported model and say why it fits the task. Use current pricing and the amount of text the model will read to estimate the cost per trace and for the proposed test. Say when a price is uncertain. Use the budget the user gave or ask for a budget before spending. Agree on the model and test budget before a model call.
5. **Check the inputs for free.** Read the source, settings and effective recipe together. Use the guide's version of `npx @glassray/evaluator` with `--stages-only --show prompt,pieces` on just enough examples to check the inputs and skips. Pass the actual settings, recipe and any context the code uses. Check that the code sends `ctx.recipe` and that the rendered prompt contains the recipe text and the evidence the model needs. Fix evidence that is missing, unnecessary or too large before a model call.
6. **Try one trace first.** Use the chosen model locally if it is available. Confirm that the first trace got a decision, then check a few known hits and close comparisons. If the local route is blocked, say why and ask whether the user wants to run that model on Glassray if it is available there. Save an unpublished draft if needed to preview a hosted test. Show the preview cost and wait for approval before starting it. If Glassray cannot run the model either, offer the supported API-key route if there is one. Keep keys in the environment or use a secure credential entry flow. If the chosen model can only run locally, report its result as a local trial and agree on a Glassray-supported model before saving. Use a different model only after the user agrees, and label coding-tool runs and runs using a different model as trials. Stop retrying a route after a quota or model-access error until something changes. Tell the user when a check produces zero decisions, even if the command itself completed.
7. **Save from disk.** When the rule and scope are settled, run `check`, get an upload link with `get_evaluator_upload_link`, upload with the runner, then pass `source_upload` to `create_evaluator` or `save_evaluator_version`. Include the plain-language steps where required and verify that the saved hash matches the upload. If the model test is blocked, tell the user before saving and say the model is still untested. Keep signed links, downloaded traces and work files out of chat and version control.

Tell the user when scope is settled, the inputs are checked, or a route is blocked. End with the saved draft, exact filter, chosen model, what the examples showed, cost and any gaps. If a quick review would help decide whether to calibrate, review a small, separate sample of unread traces from the agreed filter selected without choosing by outcome. Give the sample size and the share the recipe settles as a rough estimate. Save the formal coverage score for calibration. With only picked examples, say coverage is unknown and give the counts checked, flagged, passed and skipped. Recommend whether to calibrate now and why. Start calibration if the user asks for it. Publishing or activating requires separate authorization.
